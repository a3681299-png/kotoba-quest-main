## A. ゲーム全体のフロー案

```
ログイン画面
   ↓
物語画面（クリックで進む）
   ↓
モード選択画面（物語画面をそのまま背景に）
   ├─ カードモード（条件分岐をカードで学ぶ）
   └─ 組み合わせモード（語彙を組んでプログラミングの基礎を学ぶ ＝ 語彙遠征）
```

### 意図
- ログイン直後にいきなりゲームへ入るのではなく、**モードを選ぶ画面**を挟む。
- モード選択は **新規画面**として追加するので、既存のゲーム画面の中身は触らない（＝担当間で衝突しにくい）。

### 論点
- **物語画面を「クリックで進む」**にする案は、物語画面（BattleScreen）の中身に触れるため、
  ゲーム画面担当の領域。→ 実装前に担当と要相談（勝手に変えない）。
- モード選択画面のUI（カード2枚のデザイン）は別途モックを用意。

## C. 語彙遠征（WordQuest）UX改善案 ※実装保留

> 下記はゲーム画面担当の領域。良い改善だと思うが、**提案として共有し合意後に入れる**。
> （バグ修正である「スロット2に戻る」問題だけは先に修正済み。→ `更新内容.md` 参照）

### (b) 作戦文が完成したら「作戦を実行する」ボタンを軽く点滅
- 目的: 完成後に何をすればいいか分からない状態を防ぎ、実行を促す。
- 実装イメージ:
  - 全作戦文が有効（`validatePlan` が全て valid）になったらボタンに `is-ready` クラスを付与。
  - CSS でゆっくり点滅（`prefers-reduced-motion` 配慮）。

### (c) 文法エラーのスロットを強調（赤枠）
- 目的: エラー文だけだと、6スロットのどこが原因か分かりにくい。
- 実装イメージ:
  - 検証結果 `SentenceValidation` は既に **`missingSlot`（エラー箇所）を持っている**ので、
    そのスロットのボタンに `is-error` クラスを付けて赤枠にするだけで実現可能。
- 補足: データは既に揃っているので実装コストは小さい。

## D. アカウント名・マイページ・戦闘ログ（新規提案）

> ほぼ**導線（シェル）担当の範囲**で完結する。ゲーム内部に触れる唯一の点は
> 「戦闘完了データの受け取り口（コールバック1個）」だけ。→ そこだけ合意が要る。

### 決めた方針
- **名前 = ゲーム内ハンドル名**（Googleのアカウント名とは別）。初回ログイン後に設定させ、`users/{uid}.playerName` に保存。
- **戦闘ログの対象 = 語彙遠征モードのみ先行**（カードモードは担当外なので今回対象外）。
- **保存粒度 = サマリは全件、詳細（因果ログ）は直近N件のみ**（例: N=20）。

### D-1. 名前入力画面
- ログイン後、`playerName` 未設定なら名前入力画面を出す（モード選択の手前）。
- 保存先は既存の `users/{uid}` ドキュメントに merge するだけ。`lib/firebase.ts` に
  `savePlayerName(uid, name)` を追加し、`getUserProgress` で `playerName` も読む。
- **注意**: email/passは現状Firebaseで未有効（`auth/operation-not-allowed`）。よって
  「新規アカウント作成の名前入力」ではなく「初回ログイン後のゲーム内名設定」の位置づけにする。

### D-2. データモデル（既存パターンを踏襲）
既に `users/{uid}` ドキュメントと `users/{uid}/stages/{id}` サブコレクションがある。同じ形で：

```
users/{uid}                         ← playerName を追加（既存 stageIndex と同居）
users/{uid}/battleLogs/{runId}      ← 語彙遠征1周ぶんの記録（新規サブコレクション）
   {
     seed, playedAt,
     result: "victory" | "defeat",
     totalScore,
     discoveries: string[],
     summary: [{ enemyId, victory, turns }...],   // 全戦闘のサマリ（軽い）
     detail:  [{ enemyId, strategies, logs }...]   // 直近N件だけ / 1MB制限に配慮
   }
```

- `lib/firebase.ts` に `saveBattleLog(uid, log)` / `getBattleLogs(uid)` を追加。
- **書き込みタイミング**: 毎戦ではなく **1周完了時（victory / defeat）に1回**だけ保存（コスト抑制）。
- 詳細ログ `detail` は直近N件を超えたら古いものを間引く（または summary だけ残す）。

### D-3. ゲーム内部に触れる唯一の点（要合意）
- 語彙遠征の run は、**先の実装で `history` に作戦文＋因果ログを保持**するようになった
  （`BattleRecord.strategies` / `logs`。リザルトのステージ展開UIで使用）。
- あとは `WordQuestRunScreen` の勝敗確定時に、そのデータをシェルへ渡す
  **`onRunComplete(run)` コールバックを1個足すだけ**。内部ロジックは書き換えない。
- シェル側（`App.tsx`）がそれを受けて `saveBattleLog` を呼ぶ。→ ゲーム担当にはこの
  「イベントを1個emitする」追加だけ了承をもらう形にする。

### D-4. マイページ
- 完全にシェル担当の新規画面。`App.tsx` のルーティングに追加（モード選択から開ける）。
- 表示: ハンドル名 / 進行度 / 語彙遠征の戦績一覧（`battleLogs` のサマリ）。
- 一覧の行を開くと、保存済み `detail` があれば **リザルトで作った作戦文→ログの展開UIを再利用**して表示。
- Firestore読み込みは既存同様 **1.5sタイムアウト＋localStorageフォールバック**の耐障害パターンを踏襲。

### D-5. 段階実装（担当境界順）
1. `lib/firebase.ts`：`playerName` / `battleLogs` の read/write 関数追加（インフラ、安全）。
2. 名前入力画面 + マイページ（シェル層、担当領域内で完結）。
3. `WordQuestRunScreen` に `onRunComplete` を追加し保存を接続（**ここだけ要合意**）。
4. カードモードのログ対応は将来課題（担当外なので今回スコープ外）。
